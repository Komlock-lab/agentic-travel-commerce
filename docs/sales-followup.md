# Sales Follow-up Guide

## 1. Role of the demo

このデモはリードを大量に獲得するためではなく、すでに接点のある企業との会話を次の段階へ進めるために使います。

イベントでの役割：

- 90秒で新しい体験を理解してもらう
- 「自社ならどうなるか」という質問を引き出す

商談での役割：

- 相手の業務をMandate、Tool、Payment Railへ分解する
- PoCで何を検証し、何を作らないか合意する
- 必要なパートナーと責任分界を明らかにする

## 2. One-sentence positioning

> Komlock Labは、AIの判断を、制約・承認・監査を備えた安全な経済活動へ変換します。

旅行業界向け：

> 検索Botではなく、ユーザーの予算と権限の範囲で予約・決済・変更まで完了する旅行エージェントです。

決済事業者向け：

> 人間向けCheckoutの次に、AIエージェントが安全に利用できる決済・権限レイヤーを共同で設計します。

ステーブルコイン事業者向け：

> 送金デモではなく、予約、承認、返金を含む実業務へステーブルコインを組み込むリファレンスです。

## 3. Discovery questions

### Workflow

- 現在、検索から支払いまでにユーザーは何回操作しますか
- 担当者が手作業で判断している例外は何ですか
- 在庫、価格、キャンセル条件はどのAPIから取得できますか
- 予約と決済のどちらを先に確定しますか

### Delegation

- AIに任せてもよい最大金額はいくらですか
- 必ず人間が確認すべき条件は何ですか
- 個人、部署、会社のどの単位で予算を持ちますか
- 誰が権限を発行、変更、失効できますか

### Payment

- 現在利用している決済手段と精算通貨は何ですか
- ステーブルコインを受け取る主体は誰ですか
- 返金、取消、部分返金はどのように処理していますか
- カードへのフォールバックが必要な取引は何ですか

### Risk and operations

- 誤予約や不正決済が起きた場合、誰が責任を持ちますか
- 監査で説明する必要がある情報は何ですか
- 本人確認や取引監視はどのシステムが担いますか
- PoCで本番資金や実顧客を使う必要がありますか

## 4. Mapping the conversation to a PoC

商談中の発言を、次の表へ整理します。

| 相手の情報 | PoCの設計要素 |
| --- | --- |
| 既存の予約・購買API | Agent Tool |
| 社内規定、利用条件 | Mandate / Policy |
| 承認者、金額基準 | Approval flow |
| ウォレット、カード、銀行 | Payment Adapter |
| 返金、取消業務 | State machine |
| 監査、会計要件 | Audit Store |
| KPI | PoC measurements |

この表の空欄が多い状態では、開発見積もりを先に出しません。

## 5. PoC proposal outline

商談後の提案は、以下の1ページで開始します。

1. 対象ワークフロー
2. 現在の課題
3. AIへ委譲する範囲
4. 人間が保持する判断
5. 使用するPayment Rail
6. 実装する正常系と例外系
7. 提供いただくAPI、データ、Sandbox
8. 成功指標
9. 対象外
10. 本番化に向けた未解決事項

## 6. Avoided claims

デモや商談では、次の主張を避けます。

- AIが完全に安全、自律的である
- ブロックチェーンを使えば不正がなくなる
- ステーブルコインならカードより常に安い、速い
- すべての旅行事業者へすぐ接続できる
- 法務、会計、本人確認の問題が解決済み
- 動画で表示した機能がすべて実装済み

代わりに、何を制御でき、何をPoCで検証し、何が未解決かを説明します。

## 7. Desired next step

デモ後のCTAは「お問い合わせください」ではなく、次の具体的な共同作業にします。

> 御社のワークフローを1つ選び、AIへ委譲できる決済条件と例外を90分で整理するワークショップを実施します。

ワークショップの結果として、Thin Sliceの対象、必要なAPI、決済手段、成功指標を1ページにまとめます。
